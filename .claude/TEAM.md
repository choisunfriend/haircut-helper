# GYEOL 팀 운영

## 설치

```
gyeol-team/CLAUDE.md            → 저장소 루트 (기존 CLAUDE.md가 있으면 이어붙임)
gyeol-team/.claude/agents/*.md  → 저장소의 .claude/agents/
```

`settings.json` 에 팀 기능을 켠다.

```json
{
  "env": { "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1" }
}
```

## Phase 0 — 팀 스폰 전, 리드 혼자

이 셋을 하기 전에 팀을 띄우면 팀원 보고를 검증할 수단이 없다.

### 0-1. 죽은 파일 처리

`js/06-ui-panel.js`(단수형)는 `index.html` 어디서도 참조되지 않는다.
로드되는 건 `js/06-ui-panels.js`(복수형)다. 지우거나, 최소한 첫 줄에
`/* 이 파일은 로드되지 않는다 — index.html은 06-ui-panels.js를 부른다 */` 를 넣는다.

### 0-2. 하네스 복구

ARCHITECTURE는 "Node 하네스 37/37"을 전제하는데 저장소에 `package.json` 도
테스트도 없다. 하네스가 없으면 `TaskCompleted` 훅이 검사할 게 없고, 결국
리드가 팀원의 "했습니다"를 믿는 수밖에 없다.

`npm run harness` 로 돌아가는 형태여야 한다. 하네스가 재는 건 **동일성**이다 —
"고쳐도 안 바뀌어야 할 것이 안 바뀌었는가". 정확도는 별개 표다(둘 다 필요).

### 0-3. 되돌릴 지점 만들기

git 이력이 `Add files via upload` 커밋 하나뿐이다. 팀원 넷이 동시에 편집하는데
되돌릴 지점이 없으면 사고 하나가 전부를 삼킨다. 팀 스폰 직전에 커밋한다.

### 0-4. 완료 게이트 (하네스가 생긴 뒤)

`.claude/settings.json` 의 `TaskCompleted` 훅에서 하네스를 돌리고,
실패하면 종료 코드 2로 완료 처리를 막는다. 팀원이 잘못 판단해도 통과가 안 된다.

## Phase 1 — 팀 스폰

플랜 모드로 들어간 뒤 스폰한다. 팀원이 코드를 쓰기 전에 계획을 먼저 낸다.

```
새 스타일 하나를 만든다. 레퍼런스 4뷰는 docs/refs/<style-id>/ 에 있다.

팀원 다섯을 각 에이전트 타입으로 띄워라. 이름은 타입과 같게 한다.

- measurer      (measurer 타입)      docs/refs/ 소유
- spec-author   (spec-author 타입)   js/16-style-spec-diag.js 소유
- verifier      (solve-verifier 타입) 소유 없음 · 읽기 전용
- slider        (slider-reach 타입)  js/06-ui-panels.js 소유
- scribe        (scribe 타입)        docs/*.md 소유

의존 관계를 작업 목록에 걸어라:
  measurer → spec-author → verifier → (오차 있으면 spec-author로 되돌림)
  verifier 결과가 나온 뒤에 slider가 시작한다
  scribe는 마지막, 확정된 것만 받는다

완료 조건: npm run harness 통과 + [스타일스펙·못 풂] 경고 없음.
팀원의 "완료했습니다"를 그대로 믿지 말고 verifier의 표로 확인한 뒤
완료 처리해라. 전원 보고가 올 때까지 네가 직접 구현하지 마라.
```

## 이 팀의 병렬성은 어디에 있나

솔직히 말하면 위 흐름은 **대체로 순차적**이다. 계측이 끝나야 스펙을 쓰고,
스펙이 있어야 역산을 돈다. 순차 작업에 팀을 쓰면 조율 비용만 늘어난다.

진짜 병렬이 되는 자리는 둘이다.

**첫째, 오차 원인이 갈릴 때.** verifier가 오차를 냈는데 원인이 스펙인지,
어휘인지, 두상 실측인지 모를 때. 이때는 팀원 셋을 **경쟁 가설**로 띄운다.
각자 하나씩 맡고 서로 반박하게 한다. 순차 조사는 앵커링에 걸려서 — 한 가설을
먼저 파면 그 뒤가 그쪽으로 편향된다 — 먼저 떠오른 설명에서 멈춘다.

```
[스타일스펙] 오차가 front +57.8%로 나왔다. 원인 가설이 셋이다.
팀원 셋을 띄워 각자 하나씩 맡고, 서로의 가설을 반박하게 해라.
살아남는 설명이 진짜 원인일 가능성이 높다.
```

**둘째, 스타일을 여러 개 만들 때.** 스타일끼리는 독립이라 `STYLE_SPECS`
항목만 안 겹치면 병렬이 된다. 다만 `js/16` 을 여러 팀원이 열게 되므로,
이때는 spec-author 하나가 전부 받아 쓰고 measurer만 늘리는 편이 안전하다.

**⚠ 다만 스타일을 늘리기 전에** — 어휘(`tipAt`/`lenCm`/`cut`/`perm`/`styling`/
`fade`)가 한 스타일을 정말 재현하는지가 먼저다. 어휘가 부족한 채 스타일만
늘리면 "못 적는 것" 목록이 스타일 수만큼 곱해진다.

## 팀원 수

3~5명으로 시작한다. 토큰은 팀원 수에 선형으로 늘고, 조율 비용은 그보다 빨리
는다. 집중된 셋이 산만한 다섯보다 낫다.

첫 사이클은 **measurer + verifier 둘만** 띄워보는 것도 방법이다. 둘 다 코드를
안 고치므로 사고가 안 나고, 이 팀 구조가 이 프로젝트에서 실제로 값을 내는지를
싸게 확인할 수 있다.
